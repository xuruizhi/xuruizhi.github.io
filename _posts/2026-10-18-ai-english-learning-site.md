孩子的英语资料，曾经散在四个地方：课本 PDF 在一个文件夹，课文音频在另一个，动画视频在第三个，课课练录音和答案在第四个。Wonders 和 Peppa Pig 又是另外两套目录。资料并不缺，缺的是一条把“读—练—复习—看见进步”串起来的路。

于是有了这个网站：一个只在本机运行的纯静态站点。双击一个 `bat`，浏览器打开 `http://localhost:8000`；麦克风、视频拖动、SQLite 落库都正常。没有账号，没有云同步，没有前端框架，也没有打包器。

技术栈也很朴素：原生 HTML / CSS / JavaScript，Python 的 `http.server` 加一层自写路由，SQLite 存数据，pdf.js 渲页面，jsdom 与 Playwright 做测试。

代码注释能追到 9 月底；到 10 月 18 日，仓库里留下了 24 次提交。这篇文章想拆两件事：它有哪些功能，以及 AI 编程在构建过程中到底起了什么作用。

## 一、先看全貌

导航栏一共 14 个入口，按用途可以分成四块：

- **课堂学习**：课本点读、课课练听力、单词总表、电子课本
- **课外学习**：Wonders、Prepare、Peppa Pig
- **学习工具**：Grammar、IPA
- **学习闭环**：生词本、课程包、复习本、学习分析

首页不是一张“功能介绍页”，而是一块学习仪表盘：生词本有多少词、课程包有多少句、今天有多少项待复习、最近正确率如何，点进去就是对应的模块。另有 5 套视觉主题、A4 四线三格打印练习，以及一个按“课堂 / 课外”两条线各自选择的年级下拉框。

它从一开始就不是“把课文搬上网页”的展示页。真正的重心在后半段：**生词本 → 课程包 → 练习 → 复习 → 分析**。前半段解决“看得见、听得到”，后半段解决“练得着、记得住”。

### 1. 课堂学习：把纸面课本变成可点、可听、可跟读的页面

课本点读覆盖译林版六年级上册的 8 个单元、40 个板块、159 个单词、285 个句子、17 段课文动画，配一本 115 页的电子课本。

阅读单位不是“页”，而是“节”——一个音频板块。Lead-in、Cartoon time、Sounds in focus、Story time 这些板块往往横跨 2 到 5 个印刷页，所以页面按节顺着排下来，顶部固定一条媒体栏：原音朗读和课文动画。每一句左上角叠两个按钮：🔊 点读、🎤 跟读。跟读结果在右下角浮层里出现，不打断阅读位置。

页面本身来自课本 PDF 的原始页面图片，**不做文字重排**。图文混排、分栏、标注、颜色都是教材的一部分，重排一定失真。这一点在后面几个阅读模块里被反复复用。

课课练听力则把 40 段录音的录音稿按“大题标题 / 编号小题 / 整段短文”三种块组织起来，`A:`、`B:` 这样的行内说话人会渲染成小标签。孩子听一遍，再对着稿子核对，比只看答案更接近真实使用。

单词总表除了发音，还有一个很实用的小交互：鼠标在单词上停 2 秒，浮出它的动词或名词词形变化；行尾的“＋”直接把它加进生词本。

电子课本是自建的 pdf.js 阅读器。之所以不用浏览器自带的 PDF 查看器，是因为它跑在扩展的跨域文档里，既改不了 UI，也注入不进去，更没有“手型工具”。自建之后，缩放（50%–300%）、连续滚动、拖动平移、页码跳转都说了算。代价是要自己管理内存：一本 23MB、115 页的课本，按 1240px 宽、dpr 2 渲染，一页 canvas 就是 34MB；所以只保留“视口内 ±1 页”的位图，单页像素总数封顶 500 万，滑远了就把 canvas 的宽高置零，滑回来再渲。

### 2. 课外学习：三套原版资源，一套阅读器

Wonders G2 有三块：Reading/Writing Workshop（508 页、143 段音频）、Literature Anthology（602 页、542 段音频）、Leveled Readers（4 个难度 × 30 本，每本 23 页、19 段音频）。三本书共用同一套“连续页面”阅读器，左右翻页、缩放、页码、音频跟随都是同一套逻辑。

Leveled Readers 有文字层，可以直接划选单词加进生词本；两本大书的源 PDF 字体没有 ToUnicode 映射，pdf.js 抽不出文字，界面对这个情况直说，并给出“手动输入”的入口。这种“承认限制”的处理，比假装功能完整更重要。

Prepare Level 4 是三块：Student's Book 音频 100 段（61 段有录音稿，39 段是录音稿未收录的“额外轨”）、Workbook 音频 11 段、13 段视频。录音稿可以开关，音频按 Unit 分组，目录里没收录的轨也不丢，只是标成“录音稿未收录”。

Peppa Pig 是 8 季、396 段音频的播放器，左侧目录可折叠、可搜索，右侧是播放器 + `.lrc` 同步字幕：逐句高亮、点句跳转、自动跟随。字幕只有第 1 季 52 集有，这是正常状态，不是加载失败；没有字幕的集就好好显示“没有字幕”。另外，`.lrc` 源文件的时间戳是乱序的（Whisper 分段顺序，不是时间顺序），渲染前必须按时间排序，否则高亮会乱跳。

### 3. 学习工具：Grammar 与 IPA

Grammar 不是一张静态的表，而是“规则 + 例词 + 不规则分组”的结构：过去式、过去分词、第三人称单数、现在分词、名词复数五类，每一类下面既有规则条目，也有不规则变化的分组。动词和名词的各个形态是手工整理的，生成脚本会用规则再算一遍，判断“这条属于规则变化还是不规则变化”。录入新词时，词形变化优先从有道词典取，取不到才回落到本地规则引擎——规则引擎会把 `write` 推成 `writed`、把 `deer` 推成 `deers`，这类只能靠词库。

IPA 是 48 个国际音标（英式 DJ 体系：20 个元音 + 28 个辅音）的独立学习页：总表、每个音标的详情（发音要领、例词、字母组合、易混音）、自动判分练习。音素音 48 个、例词音 325 个，例词是英音真人录音。

### 4. 学习闭环：从“见过的词”到“记住的词”

这是整个网站最花心思的部分。

**生词本**是一个纯词库管理器，不做复习调度。分组按“来源”而不是按录入时间：词条的来源存在 `tag` 里，组顺序就是来源清单的顺序；“未分组单词”是一个真实存在的组，永远排在最后。词条身份是 `(单词, 来源)` 二元组，所以同一个 `apple` 可以既在“课本 Unit 1”又在“课外阅读”里，但在同一个组里只能有一条。支持增删改、导入导出、备份、拖动排序，以及 A4 四线三格打印练习。

**课程包**是“正式学习”的单位。在生词本里勾选若干单词，一键生成课程包；课程包的单词表就是勾选的词，句子表是这些词的示例短句。生词本里对单词的修改会自动同步到引用它的课程包：改释义、音标、例句会跟着更新，删词会一并移除，改名或换组则把旧词条从课程包移除——宁可少一个词条，也不把两条词并成一条。课程包还支持子课程包、手动新建、打印练习。

**练习引擎**有 5 种模式：阅读、中译英、听写、听力、口语；5 档难度：入门、简单、中等、困难、专家，分别对应不同的提示、限时和得分倍率。题量可以是全部、5、9、12、15；支持单词练习、句子练习、子课程包练习、单题练习。答题后统一写回复习调度字段，并追加一条复习日志。

**复习本**是调度器 + 启动器。条目来源是课程包里所有单词和句子，按归一化英文跨包去重合并；同一个英文内容出现在多个课程包，只算一条，练习结果写回它的所有副本。间隔算法按每次练习的质量 `q ∈ 0..3` 调整：

```text
q = 3   一次答对、没修改、没看提示     间隔 × 2.4
q = 2   答对但看了提示 / 口语 60~89    间隔 × 1.6
q = 1   第一次答错 / 口语 < 60         间隔 ÷ 3
q = 0   跳过 / 直接看答案              间隔归 1

上限 365 天；间隔 ≥ 180 天算“毕业”，不再推荐；
答错导致间隔缩短时，自动“复活”。
```

每天每个已开启的复习模式默认推荐 10 个，也可以按模式自定义数量，或者切“仅错题”“手动选择”。按课程包视图还能批量删除复习记录。

**学习分析**直接复用复习本的 `stats()` 口径，保证“卡片说练了多少”和“复习本推荐什么”永远是同一个算法算出来的。近 14 天正确率图是手绘 SVG，没有为了两张图引入 ECharts。清除学习记录只清复习调度、日志和配置，不删课程包里的单词和句子——学习内容和学习记录是两回事。

## 三、六个关键设计

### 1. 版式是内容的一部分

课本点读、Wonders、电子课本、Peppa 的字幕，都遵循同一条原则：**能保留原版式就保留原版式**。课本和 Wonders 直接渲染 PDF 页面图片，不做文字重排；Peppa 的字幕保留原始时间轴，不重新断句。

这条原则的代价是“重”，收益是“可信”。孩子看到的页面和课堂上看到的一样，页码、图例、标注都对得上，不会出现“这个句子在书上明明在左边，怎么网页上跑右边去了”的困惑。

### 2. 发音评分：把“像不像”拆成三个可解释的指标

跟读评分不是简单地说“对 / 错”。它先把目标句和识别结果都做归一化：缩写展开（`didn't` → `did not`）、英式 / 美式异体合并（`colour` / `color`、`mum` / `mom`）、标点转空格、纯数字不参与比对。然后用编辑距离做词级对齐，把每个词标成命中、近似、替换、漏读、多读。

最终分数由三部分组成：

- **准确度** 50%：命中的词占“命中 + 替换 + 漏读 + 多读”的比例
- **完整度** 35%：命中的词占目标词数的比例
- **流利度** 15%：按 110 词/分钟的参考语速，比较实际录音时长

如果浏览器给了识别置信度，再按 85% / 15% 的权重混进去。界面上不仅给总分，还显示每个词的命中情况和发音提示。同一句反复练，只保留最高分。

这套算法当然不完美：浏览器语音识别对童声、口音、环境噪声都敏感。但它至少是**可解释的**——孩子能知道自己哪个词没读出来，而不是只看到一个冷冰冰的分数。

### 3. 数据层：删掉 localStorage，只留一个真相

这是整个项目里返工最多、也最值得写的一段。

早期版本采用“浏览器 localStorage 是真相，服务端只是镜像”的模式，而且只在“本地这个键压根不存在”时才从数据库拉。结果就是同一个键在两边各有一份，谁新谁旧没人管。表现就是“改完刷新又变回旧数据”，但界面上没有任何报错。

后来彻底反过来：**`wordarena.db` 是唯一真相**。

```text
页面启动
  └─ 同步 GET 全量数据 → 填进内存 KV
       └─ vocab / pack / review / app 等模块在脚本求值期直接读

任何改动
  └─ KV.setItem() 标记脏键
       └─ 600ms 防抖 → POST /api/save
            └─ 服务端一个 SQLite 事务写入
                 ├─ course_packs（课程包）
                 └─ 站点键（生词本 / 复习日志 / 主题 / 年级 / 语音……）
```

几个关键决定：

- **开机必须同步拉取**。业务模块是在脚本求值期读数据的，异步拉回来它们根本看不见。所以用了同步 XHR——它不优雅，但在这里是唯一能保证“第一帧之前数据就位”的办法。
- **浏览器不落盘**。正常运行时，`assets/` 里一处 `localStorage` 都不许有；只有两个一次性迁移函数会读旧数据，搬完立刻清场。连主题、年级、朗读语速、练习音效这些设备偏好，也全部进了数据库。
- **空值绝不推**。跳过 `null` 和空串，服务端再挡一道。代价是推送异步，页面在防抖窗口内被关掉就来不及推，所以加了 `pagehide` / `visibilitychange` 的兜底 flush；写完立刻 `location.reload()` 的路径，必须先 `flush(cb)` 再 reload。
- **跨标签页同步换机制**。以前靠 `storage` 事件，现在数据不在 localStorage 里，那个事件永远不会来；改成 `BroadcastChannel`，推送成功后广播键名，别的标签页重新从数据库取那几个键。
- **一个事务写两边**。课程包和站点键经常一起变，`save_all()` 用 `BEGIN IMMEDIATE` 把它们写进同一个事务，避免“课程包写进去了、生词本没写进去”的半成品状态。

数据库只有一张表：

```sql
app_data(
  key        TEXT PRIMARY KEY,   -- 人可读的键名：vocabulary / course_packs / review_log ...
  value      TEXT NOT NULL,
  updated_at TEXT NOT NULL
)
```

前端仍然用 `yl6a-vocab-v1` 这类内存键名，映射在服务端的 `STORE_KEY_MAP` 里。跨语言字段契约单独放在 `dev/fixtures/db-fields.json`：JS 的 `dbShape()` / `importFromDb()` 和 Python 的 `_merge_db_pack()` 都读它。加字段时两边一起改，否则测试会红。这是这个项目里少数“看起来多余、实际上救命”的设计。

### 4. 内容管线：不手写数据，写生成器

Wonders 的源目录有 4700 多个文件，Peppa 有 396 段音频，IPA 有 48 个音标和 325 个例词，课课练有 40 段录音稿。这些数据如果手抄，必错；而且“书架里有这本书、音频里没有”这类不一致，只有构建期才查得出来。

所以能自动化的内容尽量走生成器：

- `dev/genwonders.js` → `assets/wonders/data.js`
- `dev/genipa.js` → `assets/ipa/data.js`
- `dev/genpeppa.js` → `assets/peppa/index.js`
- `dev/genkkl.js` → `assets/kkl.js`
- `dev/gengrammar.js` → `assets/grammar.js`

Wonders / IPA / Peppa 的生成器都带 `--check` 模式：只校验产物是否过期，不写文件，测试直接调用；课课练和语法则由 `kklcheck.js`、`grammarcheck.js` 从产物侧比对。Peppa 的产物里还带一个目录清单的 sha1，`--check` 和测试都拿它跟真实目录对账，防止“加了新一集、产物忘了重生成”这种静默漂移。

Wonders 的页号映射是内容管线里最典型的一次“先验证、再写死”：

```text
音频文件名里的编号 = PDF 的“页标签”（PageLabels）
物理页 = 页标签 + 2

物理页 1 → Cover
物理页 2 → ii
物理页 3 → 1
...
```

三套 PDF 的结构完全一样。这个规则是用 PyMuPDF 读过三份文件的 `get_page_labels()`、逐页核对过的，不是猜的。之前按“第几个音频”数顺序，结果第 22 段被标成第 1 页，全错。

### 5. 没有打包器，也要有加载秩序

这个站点没有 Webpack、Vite、Rollup，也没有 TypeScript。好处是改完刷新就见效，坏处是所有加载顺序、全局变量、依赖关系都得自己管。

课本和 Wonders 的年级脚本是**按注册表在解析期同步注入**的：

```js
var files = Grades.scripts('klass');
for (var i = 0; i < files.length; i++) {
  document.write('<script src="' + files[i] + '"><\/script>');
}
```

必须用 `document.write`，因为普通动态 `<script>` 是异步的，会让 `app.js` 先跑，那时 `window.SITE_DATA` 还没影，整站白屏。代价是这段代码只能在解析期跑，不能挪进 `DOMContentLoaded`，否则会把整页冲掉。

同样的约束也出现在 pdf.js 上：锁死 UMD 版 `3.11.174`，因为 4.x / 5.x 只发 ESM，而本站没有打包器，用不了。加一个年级，只需要在 `assets/grades.js` 注册表里加一条、放好资源目录，`index.html` 一行都不用改——这是“没有打包器”换来的另一种秩序。

### 6. 测试：39 个检查，和两次“血的教训”

项目里有 39 项自动化检查：22 个 jsdom 检查、3 个 Python 测试、14 个真实 Chrome 探针。`npm test` 会把站点拷到一个临时目录，用私有数据库副本另起一个服务，跑完连目录一起删。

这不是“为了覆盖率好看”。它来自两次真实事故：

- 一次是浏览器探针直接打在 8000 端口的 live 站点上，把课程包整组替换、词库冲掉；
- 一次是收尾时执行了 `git checkout -- wordarena.db`，把当天中午新增的 44 个生词连同分组改名一起还原掉，界面上没有任何报错。

围绕数据库回滚，项目现在有三道闸：

1. `dev/dbguard.py`：比对工作区数据库、HEAD 里的数据库和基准文件，条目变少就红；
2. `.git/hooks/pre-commit`：提交里数据库比 HEAD 少数据时直接拒绝；
3. `dev/autocommit.js`：提交前跑测试、扫密钥、checkpoint 数据库，再跑一遍上面的检查。

还有一条更隐蔽的教训：**“跳过”不能算“通过”**。临时实例起不来时，14 个浏览器探针会全部 `ok: null`；旧逻辑只看失败数，于是“一个探针都没跑”也能 exit 0，自动提交照常进行。现在默认把跳过算失败，确实要降级必须显式 `ALLOW_SKIP=1`。

## 四、AI 在构建中做了什么

如果只看结果，很容易以为这是“让 AI 写一个网站”。实际过程更像：

> 人负责方向和验收，AI 负责把方向落成代码、测试和文档。

| 阶段 | AI 主要做什么 | 人主要做什么 |
| --- | --- | --- |
| 需求拆解 | 把“我要一个点读页”拆成页面、音频、句子、评分、数据落库 | 决定做什么、不做什么，判断对孩子是否真的有用 |
| 编码实现 | 跨模块写代码、补边界、保持命名和加载顺序一致 | 定架构、审关键路径、跑起来看效果 |
| 内容工程 | 写生成器、解析 PDF / 音频 / 字幕、做 OCR 与匹配 | 抽查内容、核对教材、决定“这条算不算错” |
| 调试排障 | 读日志、复现、定位、给出修复 | 提供真实现场、判断风险、拍板取舍 |
| 测试护栏 | 写 jsdom / Python / 浏览器探针，补回归 | 决定哪些行为不能坏、事故后复盘 |
| 文档沉淀 | 写 `AGENTS.md`、模块头注释、迁移说明 | 确认约定仍然成立，删掉过时的部分 |

### 1. 真正稀缺的不是“写代码”，是“跨文件的一致性”

这个站点有 29 个 JS 文件、约 2.9 万行（含生成的数据文件），一个约 2000 行的 `serve.py`，还有 `dev/` 下约 2.8 万行的测试与工具。模块之间的隐性约定非常多：

- 资源路径要**逐段** `encodeURIComponent`，不能整条编码，否则 `/` 会被编掉；
- 日期都按本地日期算，绝不能用 `toISOString()`，否则晚上八点之后会算成第二天；
- 课程包的“推上去的形状”必须能“拉下来还原”，`dbShape()` 和 `importFromDb()` 是一对；
- 新增字段必须同时改 JS 和 Python，否则 `db-fields.json` 的契约测试会红；
- 导航顺序和项数被测试断言，改导航要同步改 `route()`、`data-nav` 和两个测试。

这些约定单看都很小，但一个 2.9 万行的项目里，漏掉任何一条都会变成“界面上看不出来、数据却错了”的 bug。AI 在这里的价值，不是一次写出多少行，而是**记得住这些约定，并且在改 A 的时候顺手检查 B**。

### 2. 把口头约定变成可执行的检查

项目里有一份 `AGENTS.md`，本质上是一份“给 AI 的项目宪法”：怎么启动、怎么跑测试、数据库为什么不能回滚、探针为什么必须跑临时实例、生成产物为什么不能手改、加年级要改哪几个地方。

这份文档不是为了“给 AI 看”而写的，它是被事故逼出来的。每一次踩坑，最后都沉淀成一条可执行的规则，或者一条测试断言。比如：

- 浏览器探针必须设 `SITE_PORT=8001-8030`，撞 8000 直接拒绝；
- 测试里 Python 子进程必须强制 UTF-8，否则中文 Windows 的 cp936 会让 `✓` / `✗` 直接 `UnicodeEncodeError`；
- `wordarena.db` 入库只为了“整库随仓库走”，**它不是回滚点**。

AI 编程最值钱的地方，或许不是“生成”，而是让“每次提交都跑一遍 39 个检查”这件事变得不费劲。人很难长期坚持这种纪律，AI 可以。

### 3. 内容工程：AI 不只是写代码

项目目录里还留着两类很能说明问题的 AI 协作痕迹。

一类是 AI IDE 留下的实施计划，例如 `.trae/documents/aurora-glass-polish.md`。它不是“帮我改一下 CSS”，而是一份完整的方案：极光底色、毛玻璃顶栏、主题色块、hover 体系、微动效，逐项写清楚；最后还有一节“明确不做”——不改 `theme.js`、不改 `index.html`、不动功能模块内部样式、不额外增加主题。**先约束范围，再动手**，这比生成多少 CSS 更重要。

另一类是任务记忆，例如 `.workbuddy-ai/memory/2026-10-14.md`。它记录了一次教材配图转例句的过程：33 个词里 28 个匹配成功、写入 42 条例句，5 个词没有对应句子；还记下了两个匹配器的边界——`The Rolling Stones` 里的 `Rolling` 被误还原成 `roll`，引号包裹的 `'youth culture'` 被正则吃成 `culture'`。这些不是“代码”，却是内容工程里最费时间、最容易出错的部分。

### 4. 复盘：把事故变成护栏

这个项目里最典型的 AI 协作，不是“写一个功能”，而是“事故之后的系统性修复”。

数据库被探针冲掉之后，做法不是“下次小心点”，而是：探针改跑临时实例、`liveguard` 拒绝写 8000、`runtests` 把跳过算失败、`autocommit` 提交前 checkpoint + 比对基准。数据库被 `git checkout` 还原之后，做法不是“记住别这么干”，而是：`dbguard` 回滚探测器、pre-commit hook、autocommit 第三道检查。

这些护栏本身也是代码，也有测试（`dbguardcheck.py`、`liveguardcheck.py`）。AI 很适合做这种“把一次教训固化成一条永远生效的规则”的工作，因为它不嫌烦。

### 5. 边界：AI 不能替人做的四件事

也得把话说清楚。这个项目里，AI 不能替人做的大概有四类：

- **产品判断**：要不要做“学习分析”？复习本要不要按课程包组织？这些不是技术问题，是“孩子到底怎么学”的问题。
- **审美与体验**：5 套主题、卡片密度、动效节奏，最终都要人看一眼，觉得“舒服”才算数。
- **数据安全**：哪些数据可以进仓库、哪些操作绝对不能做、出了事怎么恢复，必须由人拍板。AI 可以执行规则，但不能替人承担后果。
- **真实世界的验收**：麦克风在真实环境里能不能用、音频对齐不准、某个词孩子就是读不对——这些只有人戴上耳机、点一遍才知道。

AI 生成的代码比例，我没有精确统计，也不觉得重要。重要的是：**它把“一个人做一个完整产品”的门槛，从“会不会写”降到了“知不知道为什么写”。**

## 五、代价与没做好的地方

这篇文章如果只讲成功，就不可信了。这个项目有不少明显的代价：

**第一，数据层返工很痛。** 从 localStorage 到“数据库唯一真相”，中间经历了迁移、设备偏好入库、迁移标记必须进库、开机零写入等一系列问题。最隐蔽的一个是：迁移标记如果只存在内存里，每次开机都会重跑一次迁移，于是每次开机都判脏、都 POST 一次，写进去的内容和库里一模一样。这类 bug 不会让界面变红，只会让数据库悄悄被覆盖。

**第二，live 数据太容易被测试碰到。** 浏览器探针会真写数据，早期默认打 8000 端口，后果是真实的词库被冲掉。现在虽然有了临时实例和端口护栏，但“测试”和“真实数据”之间的边界，仍然是这个项目里最需要小心的地方。

**第三，没有打包器的代价。** 全局变量、脚本顺序、`document.write`、UMD 版本锁定，都是真实的维护成本。加一个模块，要同时想清楚它在哪个脚本之后加载、会不会和别的模块抢 `document` 上的事件委托。项目用“约定 + 测试”扛住了，但这不代表它适合所有人。

**第四，注释密度很高。** 大量行内中文注释记录了“为什么这么做”“哪天改的”“哪个测试守着”。这对 AI 协作是好事——上下文可重建；但注释也会过期，最终还是要靠测试和代码本身。

**第五，内容仍有缺口。** Peppa 只有第 1 季有字幕；Wonders 两本大书的文字层是空的；部分音频与页面的映射仍保留 `provisional` 标记，需要人工核对。前两项在界面上如实说明，没有假装完整。

**第六，它只适合本机。** 没有多设备同步，没有账号，没有协作；数据库文件在仓库里，但那是为了“整库随仓库走”，不是备份策略。真要备份，还是得单独拷一份。

## 七、写在最后

这个网站不完美。它的代码里有大量“当时只能这么办”的妥协，有些模块的注释比代码还长，有些边界仍然靠人盯着。

但它已经在一个真实的孩子身上跑起来了：点读、跟读、听写、复习、看正确率。它解决的不是“有没有一个网站”，而是“每天愿不愿意打开它”。

如果问我 AI 编程在这个项目里最大的作用，我会说：它让一个人也能维护一个足够复杂的系统——不是因为它不会犯错，而是因为犯错之后，可以把错误变成测试、变成护栏、变成文档，然后继续往前走。

接下来想做的，不是加更多功能，而是把已有的内容补齐、把边界写清楚。毕竟，给孩子用的东西，**可靠比功能多更重要**。
